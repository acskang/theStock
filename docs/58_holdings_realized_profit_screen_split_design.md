# 보유/실현 손익 화면 분할 설계서

## 1. 문서 목적

현재 `/analysis/`의 **보유/실현 손익** 화면은 현재 보유 평가, 실현손익, 과거 매수 회고, 종목별 회고 랭킹, 매수별 상세 로그를 한 페이지에서 동시에 제공한다. 이 문서는 계산 로직을 바꾸지 않고 화면과 서비스 경계를 재정리해 다음 목표를 달성하기 위한 설계 기준이다.

- 사용자가 10초 안에 현재 손익 상태를 파악할 수 있게 한다.
- 평가손익과 실현손익을 명확히 구분한다.
- 과거 매수 회고를 독립된 분석 기능으로 분리한다.
- 무거운 분석과 큰 테이블은 필요할 때만 조회한다.
- 사이드바는 복잡해지지 않게 유지하고, 분석 영역 내부에서 이동한다.
- 기존 계산 결과와 CSV 다운로드 기능을 보존한다.
- 화면 분할 단계에서는 계산 알고리즘을 변경하지 않는다.

---

## 2. 현재 화면의 문제 정의

현재 화면은 서로 다른 시간축과 사용자 목적을 가진 세 도메인이 섞여 있다.

| 도메인 | 사용자 질문 | 시간축 | 현재 주요 데이터 |
|---|---|---|---|
| 현재 보유 평가 | 지금 무엇을 보유하고 있으며 손익 상태는 어떤가? | 현재 | `Transaction`, 종목 매핑, 현재가 snapshot |
| 실현손익 | 이미 매도해서 확정된 손익은 얼마인가? | 과거 확정 | `Transaction` 순차 원장 계산 |
| 매수 회고 | 과거 매수 판단과 추가매수 타이밍은 좋았는가? | 과거 행동 분석 | 매수 `Transaction` + `DailyPrice` |

한 화면에서 이 세 도메인을 모두 계산하고 렌더링하면 다음 문제가 생긴다.

- 첫 화면 로딩 시 사용하지 않는 고비용 분석까지 실행될 수 있다.
- KPI, 차트, 테이블이 지나치게 많아 핵심 정보가 묻힌다.
- 초보 사용자와 고급 사용자가 동일한 정보 밀도를 감당해야 한다.
- 평가손익과 실현손익이 같은 종류의 손익으로 오해될 수 있다.
- 모바일에서 넓은 테이블이 연속적으로 나타난다.
- 회고 랭킹과 선택 종목 상세 분석의 관계가 불명확하다.

---

## 3. 핵심 설계 결정

### 3.1 최종 화면 수

**5개 주 화면 + 1개 종목 상세 경로**로 분리한다.

1. 손익 대시보드
2. 현재 보유 평가
3. 실현손익
4. 매수 회고
5. 회고 랭킹
6. 매수 회고 종목 상세 — 매수 회고의 하위 화면이며 사이드바에는 노출하지 않음

### 3.2 내비게이션 원칙

사이드바에 5개 메뉴를 모두 추가하지 않는다.

- 사이드바에는 기존 `보유/실현 손익`을 **`손익 분석`**으로 변경한 단일 메뉴만 둔다.
- 모든 손익 분석 화면 상단에 공통 로컬 내비게이션을 둔다.

```text
손익 개요 | 보유 평가 | 실현손익 | 매수 회고 | 회고 랭킹
```

이 방식은 전체 사이드바의 복잡도를 늘리지 않으면서 분석 기능 간 이동을 명확하게 한다.

### 3.3 기존 URL 보존

기존 `/analysis/`는 삭제하거나 다른 URL로 보내지 않고 **손익 대시보드**로 재사용한다.

권장 URL 구조:

```text
/analysis/                              손익 대시보드
/analysis/holdings/                     현재 보유 평가
/analysis/realized/                     실현손익
/analysis/buy-review/                   매수 회고
/analysis/buy-review/ranking/           회고 랭킹
/analysis/buy-review/<stock_code>/      선택 종목 매수 회고 상세
```

권장 URL name:

```text
portfolio:profit_loss_dashboard
portfolio:holdings_valuation
portfolio:realized_profit
portfolio:buy_review
portfolio:buy_review_ranking
portfolio:buy_review_detail
```

### 3.4 계산 로직 보존

첫 분할 작업에서는 계산 결과를 바꾸지 않는다.

- 기존 보유수량·평균매수가 계산 유지
- 기존 실현손익 계산 유지
- 기존 회고 점수와 판정 기준 유지
- 기존 CSV 결과 유지
- 기존 가격 조회 fallback 유지

화면 분할과 계산 개선을 동시에 진행하면 결과 차이가 UI 이동 때문인지 알고리즘 변경 때문인지 구분하기 어렵다. 계산 개선은 화면 분리 완료 후 별도 단계로 한다.

## 5. 화면별 상세 설계

## 5.1 화면 1 — 손익 대시보드

### 역할

사용자가 가장 먼저 들어오는 상태 요약 화면이다. 여기서는 깊은 분석을 하지 않고 현재 손익과 확정 손익의 방향만 빠르게 보여준다.

### 사용자 질문

- 전체적으로 수익인가 손실인가?
- 아직 보유 중인 손익과 이미 확정된 손익은 각각 얼마인가?
- 어떤 종목을 먼저 확인해야 하는가?
- 어느 상세 화면으로 이동해야 하는가?

### 포함 정보

상단 KPI:

- 총 장부가
- 총 평가금액
- 총 평가손익
- 평가손익률
- 총 실현손익
- 총 손익 — 통화가 동일하거나 명시적 환산 기준이 있을 때만 표시
- 보유 종목 수
- 손실 보유 종목 수
- 가격 조회 실패 종목 수

중간 요약:

- 평가수익 상위 5개
- 평가손실 상위 5개
- 실현수익 상위 5개
- 실현손실 상위 5개

하단 진입 링크:

- 보유 평가 자세히 보기
- 실현손익 자세히 보기
- 매수 회고 분석하기
- 회고 랭킹 보기

### 포함하지 않는 정보

- 매수별 상세 회고 로그
- 전체 회고 랭킹 테이블
- 실현손익 거래별 계산 상세
- DailyPrice 기반 무거운 회고 분석

### 성능 원칙

- GET 요청에서 회고 분석을 실행하지 않는다.
- 보유/실현 summary만 계산한다.
- 가격 조회 일부 실패 시에도 화면 전체를 실패시키지 않는다.

## 5.2 화면 2 — 현재 보유 평가

### 역할

아직 매도하지 않은 종목의 평가 상태를 확인하는 화면이다.

### 사용자 질문

- 어떤 종목을 얼마나 보유하고 있는가?
- 평균매수가와 현재가는 얼마인가?
- 손실률 또는 평가손실이 큰 종목은 무엇인가?
- 가격 데이터가 실패한 종목은 무엇인가?

### KPI

- 총 보유 종목 수
- 총 장부가
- 총 평가금액
- 총 평가손익
- 평가손익률
- 수익 종목 수
- 손실 종목 수
- 가격 미확인 종목 수

### 테이블 기본 컬럼

- 종목명
- 보유수량
- 평균매수가
- 현재가
- 장부가
- 평가금액
- 평가손익
- 수익률
- 가격 상태
- 상세 링크

기본 화면에서는 티커를 보조 정보로만 표시한다.

### 필터/정렬

- 전체 / 수익 / 손실 / 가격 오류
- 평가손익순
- 수익률순
- 종목명순

### 링크

- 보유종목 상담 상세
- 매수 회고 종목 상세
- 거래 원장 보기

### 데이터 상태 표시

각 행 또는 화면 상단에 다음을 사용자 친화적으로 표시한다.

- 정상
- 최신 가격 없음
- 종목 매핑 필요
- 가격 조회 실패

내부 예외 문자열은 표시하지 않는다.

---

## 5.3 화면 3 — 실현손익

### 역할

이미 매도해 확정된 결과를 검증하는 화면이다.

### 사용자 질문

- 지금까지 확정된 손익은 얼마인가?
- 어떤 종목에서 수익 또는 손실을 확정했는가?
- 특정 매도 거래의 원가와 손익은 어떻게 계산됐는가?
- 계산 경고가 있는 거래는 무엇인가?

### KPI

- 총 실현 매도수량
- 총 매도금액
- 총 매도원가
- 총 실현손익
- 실현손익률
- 수익 종목 수
- 손실 종목 수
- 계산 경고 건수

### 필터

- 시작일 / 종료일
- 종목명
- 전체 / 수익 / 손실 / 경고

### 메인 테이블 — 종목별 실현손익

- 종목명
- 실현수량
- 매도금액
- 매도원가
- 실현손익
- 수익률
- 매도 건수
- 상세 보기

### 상세 테이블 — 매도별 계산

기본 접힘 상태로 둔다.

- 매도시각
- 종목명
- 매도수량
- 매도가
- 평균매수가
- 매도금액
- 매도원가
- 실현손익
- 수익률
- 비고/경고

### CSV

현재 필터 조건을 그대로 사용해 CSV를 다운로드한다.

### 개념 구분

화면 상단에 다음 설명을 고정한다.

- 평가손익: 현재 보유 중인 미확정 손익
- 실현손익: 매도 완료로 확정된 손익

## 5.4 화면 4 — 매수 회고

### 역할

선택한 종목에서 사용자의 매수 습관과 사후 성과를 분석한다.

### 사용자 질문

- 이 종목에서 매수 판단이 전반적으로 좋았는가?
- 너무 일찍 물타기했는가?
- 매수 후 평균적으로 얼마나 더 하락했는가?
- 손익분기나 고점까지 얼마나 걸렸는가?
- 다음에 피해야 할 패턴은 무엇인가?

### 화면 진입 구조

첫 진입 시 종목 선택과 간단한 안내만 보여준다. 종목을 선택한 뒤 상세 분석을 조회한다.

### 상단 영역

- 종목 선택
- 판정 필터
  - 전체
  - 잘한 매수
  - 보통 매수
  - 아쉬운 매수
  - 판단 보류
- 분석 기간/데이터 커버리지
- CSV 다운로드

### 1순위 노출 — 회고 인사이트

- headline
- 평균 20일 성과
- 평균 20일 최대 낙폭
- 가장 자주 나온 판정
- 평가 완료 건수
- 데이터 부족 건수

### 2순위 노출 — 가격 흐름과 매수 시점

- 전체 가격 흐름
- 매수 marker
- 잘한/보통/아쉬운/보류 색상
- 저점/고점/최근 가격
- marker 선택 시 해당 매수 요약

초기 분리 단계에서는 기존 SVG를 유지한다. D3.js 전환은 후속 고도화 단계로 둔다.

### 3순위 노출 — 행동 인사이트

- 사유 유형 요약
- 실행 품질 지표
- 가장 좋았던 매수
- 가장 아쉬웠던 매수

고급 지표는 accordion으로 기본 접힘 처리한다.

### 4순위 노출 — 매수별 상세 로그

기본 접힘 상태로 둔다.

- 매수시각
- 매수 구분
- 수량
- 매수가
- 매수 전/후 평단
- 5/20/60일 성과
- 20일 최대상승/하락
- 판정
- 점수
- 손익분기/고점 도달일
- sparkline

모바일에서는 상세 행을 카드 또는 expandable row로 표시한다.

---

## 5.5 화면 5 — 회고 랭킹

### 역할

종목별 매수 판단 품질을 비교하고 상세 분석 대상을 고르는 화면이다.

### 사용자 질문

- 어떤 종목에서 매수 판단이 좋았는가?
- 반복적으로 좋지 않은 타이밍에 매수한 종목은 무엇인가?
- 표본이 충분한 결과와 부족한 결과를 구분할 수 있는가?
- 다음으로 어떤 종목을 자세히 분석해야 하는가?

### 필터/정렬

- 평균 회고 점수
- 실행 일관성
- 좋은 매수 비율
- 평균 20일 성과
- 평가 완료 건수 최소값

### 테이블

- 순위
- 종목명
- 평균 회고 점수
- 평균 20일 성과
- 좋은 매수 비율
- 잘한 매수 건수
- 아쉬운 매수 건수
- 평가 완료 건수
- 신뢰도
- 일관성
- 상세 링크

### Badge 정책

첫 단계에서는 badge를 다음 3개 이내로 축소한다.

- 현재 정렬 1위
- 일관성 우수
- 표본 부족

나머지 1위 badge는 tooltip 또는 상세 화면으로 이동한다.

### CSV

현재 정렬/필터 조건으로 랭킹 CSV를 다운로드한다.

## 5.6 하위 화면 — 매수 회고 종목 상세

### 역할

랭킹이나 보유 평가 화면에서 선택한 한 종목의 회고 분석을 직접 연다.

### URL

```text
/analysis/buy-review/<stock_code>/
```

### 포함 정보

- 선택 종목 회고 인사이트
- 가격 흐름과 매수 시점
- 사유 유형
- 실행 품질 지표
- best/worst 사례
- 매수별 상세 로그

### 이동 관계

- 회고 랭킹 → 종목 상세
- 보유 평가 → 종목 상세
- 종목 상세 → 회고 랭킹
- 종목 상세 → 거래 원장

## 6. 기능 간 관계와 데이터 흐름

```text
portfolio.Transaction
        │
        ├── 거래 원장/포지션 계산 ──> 현재 보유 평가
        │                         └─> 손익 대시보드의 평가 요약
        │
        ├── 순차 매도 원가 계산 ───> 실현손익
        │                         └─> 손익 대시보드의 실현 요약
        │
        └── 매수 거래 추출
                  + marketdata.DailyPrice
                  └─> 매수 회고 엔진
                         ├─> 종목별 회고 랭킹
                         └─> 선택 종목 회고 상세

현재가 snapshot / 가격 provider
        └─> 현재 보유 평가에만 사용
```

### 관계 원칙

- 손익 대시보드는 상세 결과를 다시 계산하지 않고 각 도메인의 summary만 사용한다.
- 보유 평가와 실현손익은 동일한 거래 원장을 사용하지만 계산 목적은 분리한다.
- 매수 회고는 매수 거래와 DailyPrice를 사용하며 실현손익 계산에 의존하지 않는다.
- 회고 랭킹과 회고 상세는 같은 회고 엔진의 집계 수준만 다르게 사용한다.
- 화면별 view에 동일 계산을 복사하지 않는다.

## 7. 권장 서비스 구조

기존 계산 함수가 이미 다른 위치에 있으면 새로 중복 구현하지 말고 이동 또는 wrapper 방식으로 정리한다.

```text
portfolio/
├─ services/
│  ├─ portfolio_ledger.py
│  ├─ holdings_valuation.py
│  ├─ realized_profit.py
│  └─ buy_review.py
│
├─ selectors/
│  └─ profit_loss.py
│
├─ views/
│  └─ analysis.py              또는 기존 views.py 내 명확한 함수 분리
│
└─ templates/portfolio/analysis/
   ├─ base.html
   ├─ dashboard.html
   ├─ holdings.html
   ├─ realized.html
   ├─ buy_review.html
   ├─ buy_review_ranking.html
   ├─ buy_review_detail.html
   └─ partials/
      ├─ _analysis_nav.html
      ├─ _warning_banner.html
      ├─ _kpi_card.html
      ├─ _holdings_table.html
      ├─ _realized_table.html
      ├─ _review_chart.html
      └─ _review_trade_table.html
```

권장 public service contract:

```text
build_user_portfolio_ledger(user)
get_holdings_valuation(user, filters=None)
get_holdings_summary(user)
get_realized_profit(user, filters=None)
get_realized_summary(user)
get_buy_review_ranking(user, sort, filters=None)
get_buy_review_detail(user, stock_code, filters=None)
```

### 중요한 구현 규칙

- service는 `request` 객체에 의존하지 않는다.
- view는 필터 parsing, 권한, response 렌더링만 담당한다.
- template은 계산하지 않는다.
- dashboard는 detail row 전체를 받지 않는다.
- 사용자 범위는 모든 query에서 `request.user` 기준으로 제한한다.

## 8. 화면 공통 UI 규칙

### 8.1 공통 로컬 내비게이션

모든 분석 화면 상단에 동일하게 표시한다.

```text
손익 개요 | 보유 평가 | 실현손익 | 매수 회고 | 회고 랭킹
```

현재 화면은 active 상태로 표시한다.

### 8.2 종목 표시

- 기본: 종목명
- 보조: 종목코드 또는 티커
- 종목코드는 작은 보조 텍스트나 tooltip로 표시
- 필터 검색은 종목명 중심

### 8.3 상세 정보

- 요약 먼저
- 상세 테이블은 기본 접힘
- 모바일에서는 카드 또는 expandable row
- 넓은 table은 `overflow-x-auto`

### 8.4 손익 색상

- 양수: 수익
- 음수: 손실
- 0 또는 미확정: 중립
- 색상만으로 의미를 전달하지 않고 `수익`, `손실`, `미확인` text를 함께 표시

### 8.5 데이터 출처와 시각

화면마다 다음을 명시한다.

- 거래 원장 기준 시각
- 현재가 조회 시각
- 가격 source
- DailyPrice 분석 범위
- 데이터 누락/경고 건수

### 8.6 다중 통화

- KRW와 USD를 단순 합산하지 않는다.
- 환산하지 않는 초기 단계에서는 통화별 합계를 분리한다.
- 환산 합계를 제공할 경우 환율 source와 기준 시각을 명시한다.

## 9. 고비용 기능 로딩 원칙

현재 거대 화면을 단순히 여러 template로 나누기만 하면 서버 계산 비용이 그대로 남을 수 있다. 각 URL은 필요한 계산만 실행해야 한다.

| 화면 | GET 시 실행할 계산 | 실행하지 않을 계산 |
|---|---|---|
| 손익 대시보드 | 보유 summary, 실현 summary | DailyPrice 회고 상세 |
| 보유 평가 | 포지션 계산, 현재가 조회 | 실현 상세, 회고 분석 |
| 실현손익 | 원장 기반 실현손익 | 현재가 조회, 회고 분석 |
| 매수 회고 | 선택 종목의 회고 분석 | 전체 종목 ranking 전체 계산이 불필요하면 제외 |
| 회고 랭킹 | 종목별 집계 | 선택 종목의 매수별 상세 로그 |

### HTMX 권장 영역

- 보유 평가 필터 변경
- 실현손익 상세 펼치기
- 매수 회고 종목 선택
- 회고 랭킹 정렬
- 매수별 상세 로그 펼치기

JavaScript가 없어도 GET form submit으로 동작해야 한다.

## 10. 레거시 화면 전환 전략

### 10.1 전환 중

- 기존 `/analysis/` 화면을 즉시 삭제하지 않는다.
- 새 화면이 순차적으로 완성될 때까지 기존 계산 함수를 유지한다.
- 각 섹션이 새 URL로 이동하면 기존 화면에서는 해당 섹션 대신 새 화면 링크를 표시한다.

### 10.2 전환 완료 후

- `/analysis/`는 손익 대시보드가 된다.
- 기존 거대 template는 제거하거나 임시 보관 후 삭제한다.
- 동일한 계산이 구 화면과 신 화면에서 두 번 유지되지 않게 한다.
- 기존 북마크는 `/analysis/`에서 새 대시보드로 자연스럽게 이어진다.

### 10.3 금지

- 기존 화면을 복사해 5개 화면에 동일 계산 코드를 중복 배치
- 화면별로 실현손익 계산식을 다르게 구현
- 회고 점수 기준을 UI 분리와 동시에 변경
- old/new 화면을 장기간 동시에 운영하며 결과 차이를 방치

완료 기준:

## 13. 완료 기준

### 기능 기준

- 기존 화면의 모든 기능이 새 화면 중 하나에 존재한다.
- 보유 평가, 실현손익, 회고 계산 결과가 기존과 동일하다.
- 기존 CSV 다운로드 기능이 유지된다.
- 종목 상세와 거래 원장 이동 링크가 유지된다.

### UX 기준

- `/analysis/`에서 전체 상태를 빠르게 이해할 수 있다.
- 현재 보유와 확정 손익을 혼동하지 않는다.
- 회고 상세 table이 기본 노출되지 않는다.
- 종목명 중심으로 표시한다.
- 모바일에서 table이 레이아웃을 깨뜨리지 않는다.

### 성능 기준

- 대시보드 GET에서 DailyPrice 회고 상세 분석을 실행하지 않는다.
- 보유 평가 화면에서 실현 상세와 회고 분석을 실행하지 않는다.
- 실현손익 화면에서 현재가 조회를 실행하지 않는다.
- 선택하지 않은 종목의 회고 상세를 렌더링하지 않는다.

### 안전 기준

- 모든 화면은 로그인 사용자 데이터만 조회한다.
- read-only 분석 화면에 매수/매도 실행 버튼을 두지 않는다.
- 내부 예외 문자열을 사용자에게 표시하지 않는다.
- 서로 다른 통화를 기준 없이 합산하지 않는다.

## 15. 최종 권고

최종적으로 사이드바는 `손익 분석` 하나만 유지하고, 분석 영역 내부를 다섯 화면으로 나누는 구조가 가장 적합하다.

```text
손익 분석
├─ 손익 개요
├─ 보유 평가
├─ 실현손익
├─ 매수 회고
└─ 회고 랭킹
```

구현은 **보유 평가 → 실현손익 → 손익 대시보드 → 회고 랭킹 → 매수 회고 상세 → 레거시 제거** 순서로 진행한다.

이 순서는 다음 장점이 있다.

- 가장 혼동이 큰 평가손익/실현손익을 먼저 분리한다.
- 사용자가 단계마다 운영 화면에서 결과를 확인할 수 있다.
- 무거운 회고 분석을 마지막에 이동해 초기 위험을 줄인다.
- 기존 `/analysis/` URL을 유지해 메뉴와 북마크를 깨뜨리지 않는다.
- UI 분할과 계산 알고리즘 변경을 분리해 결과 불일치를 방지한다.
